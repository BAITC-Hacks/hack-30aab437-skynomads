## Goal

Реализовать проверяемый вертикальный slice, где расчёт является детерминированным, а AI объясняет уже рассчитанные результаты.

## User Flow

1. Открыть симулятор и увидеть исходные районы, меры и бюджет 100 (`R-01`).
2. Выбрать пять различных мер; у районных указать район, у городских район не выбирать (`R-02`).
3. Увидеть расход и причины недопустимости набора; допустимый набор передать в расчёт (`R-02`, `R-03`, `R-06`).
4. Получить Score, существенные изменения показателей и объяснение от реального AI (`R-04`, `R-05`).

## UI Behavior

- Показать в React SPA каталог с направлением, названием, типом и ценой меры, исходные показатели районов и общий бюджет (`R-01`).
- Для районных мер спрашивать один из пяти районов, для городских район не запрашивать. Показывать выбранные пять решений, общую стоимость и результат либо конкретные ошибки (`R-02`, `R-03`, `R-06`).
- В результате обозначать Score и объяснение; если AI не ответил, не показывать статичный текст как сгенерированный AI-анализ (`R-04`, `R-05`).

## Backend Behavior

Доменную проверку набора, расчёт и защищённый ключом вызов AI разместить за серверной границей Express. Конкретный маршрут согласовать перед реализацией; не раскрывать ключ в React SPA.

- Проверить весь набор перед расчётом: ровно пять разных известных мер; районное/городское назначение, лимит по направлениям, конфликты, бюджет (`R-02`, `R-03`).
- Для каждой пары район × показатель взять исходное значение, добавить эффекты выбранных районных мер только в их районе и городских — во всех пяти. Каждый полный эффект умножить на `(8 - lagQuarters) / 8`; синергии добавить в районе первой меры пары без множителя лага. Затем `clip(…, 0, 100)` (`R-04`).
- Вычислить оценку района по весам показателей, `D_avg` по долям населения, минимум районных оценок и `N_crit` — число значений строго ниже 40. Итог: `0.7 * D_avg + 0.3 * min(D_d) - N_crit`. Остаток бюджета не прибавлять (`R-04`).
- Передать AI уже рассчитанные значения: исходный/итоговый Score, дельты по районам и показателям, вклад выбранных мер и ограничения интерпретации синтетических данных. Запросить объяснение сильных сторон, рисков и компромиссов, без самостоятельного расчёта и выдуманных чисел (`R-05`).

## Data Model Impact

- Полный исходный набор — `docs/data-set.json`; backend читает только необходимую проекцию `apps/backend/db.json` (пять районов, десять определений показателей, 14 мер, три синергии, три конфликта, веса и правила). Тест сверяет её с полным набором, чтобы копия не расходилась с источником (`R-01`, `R-04`).
- Временный выбор представляет пять элементов `{ measureId, district }`, где `district` — название района для районной меры, а для городской отсутствует/`null`. Вычисленный результат содержит Score и данные для объяснения; формат долговременного хранения не требуется для MVP.

## API Or Action Contract

Контракт поведения для вызова из React SPA к Express API; точный HTTP-маршрут ещё не утверждён:

- Вход: набор решений `{ measureId, district }`; ровно пять элементов. Стоимость и эффекты берутся из каталога, а не доверяются полям пользовательского ввода (`R-02`–`R-04`).
- Успех: расходы/остаток бюджета, Score, районные/показательные изменения, AI-объяснение или явный статус его недоступности (`R-04`, `R-05`).
- Ошибка валидации: понятные причины, Score не вычисляется (`R-02`, `R-03`, `R-06`). Конкретный формат ответа и маршрут согласовать при определении API.

## Validation Rules

- Бюджет 100, ровно пять мер без повторов, минимум три направления и не больше двух мер одного направления; выбор района строго по scope, только известные ID и районы (`R-01`–`R-03`).
- M1 и M3 несовместимы независимо от районов; M4/M7 и M5/M13 несовместимы лишь при совпадении района. Применять три синергии только когда обе меры выбраны; бонус в районе первой меры пары (`R-02`, `R-04`).
- Невалидный набор возвращает причину без Score; порядок решений на Score не влияет (`R-02`, `R-06`).

## States And Edge Cases

- Пустой ввод/неполный набор, неверный район, дубликат, конфликт, переполнение бюджета → понятная ошибка без Score.
- Необходимая AI-конфигурация отсутствует или вызов завершился ошибкой → явное сообщение, никаких подставных ответов; уже вычисленные числа не заменять AI-оценками.
- Значение 40 не является критичным; 39.999… — критично. Отрицательный эффект M11 на T1 учитывать; суммарные значения обрезать в 0–100 (`R-04`).

## Acceptance Criteria

- `AC-01` (`R-01`, `R-03`): одинаковый бюджет и начальные данные; 95 допустимо, более 100 недопустимо.
- `AC-02` (`R-02`, `R-06`): пример M7/Нура, M8/Нура, M10/Нура, M12/город, M5/Сарыарка принимается; нарушения правил сообщаются по существу.
- `AC-03` (`R-04`): базовый Score ≈52.56, пример ≈56.5; лаг, синергия, лимиты и штраф влияют на числа строго по датасету. Точный расчёт данных для примера даёт 56.5431 до округления.
- `AC-04` (`R-05`, `R-06`): успешный реальный AI-вызов объясняет результат; неуспешный не имитируется и виден как ошибка.
- `AC-05` (`R-07`): чистый запуск и один невалидный ввод повторяются по README, конфигурация описана без секретов.

## Test Cases

1. (`AC-01`–`AC-03`) Рассчитать пустой базовый набор только как контроль модели: 52.56 после округления; набор M7/Нура, M8/Нура, M10/Нура, M12/город, M5/Сарыарка стоит 95, синергия M10+M12 работает, Score до округления ≈56.5431. Пустой набор как пользовательский ввод отвергается.
2. (`AC-02`) Отклонять четыре/шесть мер, повтор M7, неизвестный ID/район, район у M12, отсутствие района у M7, три меры «Соцсфера».
3. (`AC-01`, `AC-02`) Отклонять превышение 100, M1/M3 при любом выборе районов, M4/M7 и M5/M13 в одном районе; разрешать последние пары в разных районах при соблюдении остальных правил.
4. (`AC-03`) Проверить городскую меру на всех районах, лаг M7 `5/8`, бонус M10+M12 `B1 +2` в Нуре без лага, штраф строго при `< 40`, границы `0..100`, неизменность Score при перестановке решений.
5. (`AC-04`) Продемонстрировать настоящий AI-вызов; при сбое/отсутствии конфигурации проверить понятный статус вместо фиктивного ответа.
6. (`AC-05`) Другой участник запускает проект и повторяет пример и ошибочный ввод только по README и безопасной конфигурации.

## Implementation Notes

- В проект перенесён React/Express scaffold: `yarn typecheck` и `yarn build` проходят, CI/тестового скрипта нет. Доступный AI-провайдер и API-контракт требуют подтверждения до начала реализации; план не предписывает несуществующие библиотеки или доступы.
- Приоритет: первый сквозной сценарий с реальным вызовом AI, затем ошибочные входы и воспроизводимость. Не превращать слой расчёта в mock; внешние неключевые заглушки, если появятся, честно отметить в README.
- Для эталона не требовать округление `56.5431` в `56.5`: это приблизительное число в исходнике; UI отображает два знака после запятой (56.54), расчёт ведётся с полной точностью.
